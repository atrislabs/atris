# the till: the first civilian verifier

One feature. Written 2026-07-09 for handoff to a high-tier engine on 2026-07-10.
Owner: Keshav. Lane: protected (payments). Nothing here builds without his go
on the specific payment surface.

## what it is, in one sentence

Atris learns to verify "money arrived", so a mission's receipt can be a paid
booking instead of a passing test.

## why this feature and not another

- Every loop in the system today verifies in developer currency (tests, CI, git).
  The roadmap's next rung is civilian currency, and money is the least ambiguous
  civilian signal that exists.
- It completes a chain that already works end to end except for the last link:
  `atris meet` onboards a stranger, `atris avail` gives them a live /book page,
  the mission loop works their wish. The till closes the loop: booked and paid
  becomes a receipt the system can check itself.
- It is the gate on the open wish "1K subscribers at $100/mo" (captured 4x).
  No combination of existing features produces revenue verification. This is a
  true gap, confirmed by the alpha judge 2026-07-09.

## the user

The stranger from the desert who just got onboarded by `atris meet`, and Keshav,
whose mission "first stranger pays for atris" currently has no honest way to
know it succeeded.

## the shape (bounded)

1. Payment attach: a /book page can carry a payment link (Stripe payment link,
   simplest possible integration, no custom checkout). Configured through the
   existing avail settings, off by default.
2. Read-only till adapter: `lib/till.js` (name flexible) that answers one
   question: "did a payment matching <reference> arrive since <time>?" Read
   only. No refunds, no charges, no writes to Stripe, ever.
3. Verifier verb: `atris till check <reference>` exits 0 when the payment
   exists, nonzero when it does not, so any mission can use it as `--verify`.
4. Receipt: when a mission's till verifier passes, the receipt names the
   amount, the payer's booking (not identity beyond what the booking shows),
   and the timestamp. That receipt is the first civilian receipt in the system.

## non-goals (slop fence)

- No subscription management, no plans, no billing portal. One payment link.
- No storing card data or payer PII beyond the booking reference.
- No auto-pricing, no discounts, no invoicing.
- No new UI. Terminal and the existing /book page only.
- Not multiplayer. One operator, one till.

## verifier for the feature itself

- Unit: till adapter answers correctly against a recorded fixture (hermetic,
  no live API in tests).
- Integration: one real payment of $1 by Keshav through a test /book page,
  verified by `atris till check` exiting 0, receipt generated. That single
  receipt is the acceptance proof. Human observed.
- CI: all new tests hermetic, green on GitHub Actions (cite the run id).

## protected-lane boundaries (explicit, per doctrine)

- API keys live in the existing credentials store, never in the repo.
- The engine building this does NOT self-land. Orchestrator reviews the diff
  before merge (payments lane).
- Any scope beyond read-only payment verification requires a new written go
  from Keshav.

## what done unlocks

The stranger-pays mission gets an honest stop condition. Stage 3 of the
five-stage roadmap (company faces outward, verify revenue) gets its first
working organ. And the sentence "a wish is a debt repaid with receipts" becomes
true in dollars.
